# The inspection console — what every number means

`viewer/dashboard.html`, served by `jetson/serve_scan.py`.

```bash
python3 serve_scan.py                 # scan mode,  ~6.5 s per position
python3 serve_scan.py --mode live     # live preview, ~10 fps
```

Open `http://<jetson-ip>:8081/`. The page is plain HTML and JavaScript with no
build step and no dependencies.

## Header

| Element | Meaning |
|---|---|
| **CONNECTED** | `/status.json` answered. Goes stale if the scan loop dies |
| **demo · synthetic** (amber) | Data is from `tools/demo_server.py`, **not real hardware** |
| **LIVE PREVIEW** (blue) | Running in live mode — see *Modes* below |
| `scan` | Scan positions completed (scan mode) or frames rendered (live) |
| `infer` | Inference time per camera |
| `gpu` | Current GPU clock. Should read **1020 MHz**; 306 MHz means `jetson_clocks` was lost in a reboot and everything is ~2.6× slower |

The demo badge exists because a demo that looks like real inference but isn't is
a trap — someone asks "is that live?" and the honest answer has to be instant.

## Composite stage

Three camera frames side by side with detections overlaid: **red fill** for
detected pixels, **yellow outline** around each component.

Captioned on the image itself:

> `DISPLAY COMPOSITE — detection is per-camera`

**This is the most important statement on the page.** The three images are
placed next to each other *after* inference. Nothing is stitched before the
model sees it, because a blended seam is a long thin dark line — exactly what a
crack detector fires on. See [02-perception.md](02-perception.md) §1.

The **verdict badge** (top right) reads `CRACK` or `CLEAR`: whether any single
camera exceeded `alert-frac` (default 1% coverage).

---

## Verdict panel

| Field | Meaning |
|---|---|
| **CRACK / CLEAR** | Any camera above the alert threshold |
| *n* components above threshold | Connected components surviving all filtering, summed across cameras |

## Measurements

| Field | Meaning | Caveats |
|---|---|---|
| **coverage** | Mean fraction of pixels marked as crack | **Averaged across cameras, not pooled over pixels.** The three see different ground, so pooling would let one busy camera be diluted by two empty ones in a way that depends on frame size rather than the surface |
| **widest crack** | Largest crack width found, in mm | 95th percentile of the distance-transform ridge. **Only as correct as the standoff** — see below |
| **components** | Count of surviving connected components | After size, shape and (on branch) verification filtering |
| **swath** | Total ground width covered by all cameras | Derived from standoff and field of view |
| **resolution** | Ground sample distance, mm/px | The limit on what can be measured at all |

> ### The caveat that matters most
>
> `resolution` and every millimetre figure are derived from an **assumed
> standoff** (default 0.40 m). Width scales **linearly** with it: a camera
> actually at 0.15 m reports every crack ~2.7× too wide.
>
> Fix by measuring the distance, or by photographing something of known width
> (a bank card is 85.60 mm) and passing `--mm-per-px`.

Smallest resolvable crack is about **2 px**: ~0.59 mm in scan mode, ~1.65 mm in
live preview.

## Pipeline

| Field | Meaning |
|---|---|
| **tiles / camera** | 15 at 1080p scan; 1 in live preview |
| **inference** | GPU time per camera per cycle |
| **scan cycle** / **frame rate** | The label changes with the mode. Scan mode shows seconds per position (~6.5 s, ~90% of it capture). Live shows fps |
| **threshold** | Probability threshold, applied in logit space |
| **min area** | Minimum component size in pixels. **Rescales with the mode** — 600 at native 1080p, 76 in live preview, because the preview's pixels are ~2.8× coarser |

## System

| Field | Meaning |
|---|---|
| **power mode** | Should read `MAXN_SUPER`. Note mode 0 is **15 W**, not maximum, on this board |
| **gpu clock** | 1020 MHz when `jetson_clocks` is applied |
| **soc temp** | Hottest thermal zone |
| **uptime** | Since the scan loop started, not since boot |

## Camera strip

One panel per camera, showing the **whole frame** (never cropped — a cropped
view next to a whole-frame coverage percentage invites misreading).

| Element | Meaning |
|---|---|
| Status dot | green = streaming and clear, red = streaming with a detection |
| `exp` | `exposure_time_absolute`. Snaps to the ×2 ladder **38, 77, 156, 312, 624** — intermediate values are not reachable while streaming |
| `gain` | Sensor gain, 0–160. **Should be near 0.** Gain amplifies read noise into thin bright streaks, which is the exact false-positive signature |
| `%` | That camera's coverage |

Seeing `exp 156 · gain 0` on all three is the healthy state.

---

## Event log

Timestamped, newest at the bottom, with pause and clear.

| Level | Meaning |
|---|---|
| `INFO` | Startup configuration, and a heartbeat every 4th scan (~27 s) |
| `CRACK` | Verdict changed to crack — names the camera, widest width, coverage, component count |
| `CLEAR` | Verdict changed back |
| `WARN` | Exposure failed to converge, or a scan raised an exception |

Logging is **on change plus a heartbeat**. Logging every scan would push a line
every ~6 s and bury the one that matters; logging only on change would leave the
panel silent through a long clear run, which on screen is indistinguishable from
a crashed loop.

## Modes — the two sets of numbers are not comparable

| | scan | live preview |
|---|---|---|
| Cameras | one at a time, 1080p | all three, 640×480, held open |
| Rate | ~6.5 s per position | ~10 fps |
| Detection | 15 native tiles | centre-crop → 512, 1 tile |
| mm/px | 0.29 | 0.83 |
| Smallest crack | ~0.59 mm | ~1.65 mm |
| Use for | **measurement** | **aiming and monitoring** |

Because both publish `widest_mm`, `coverage` and `components` under the same
names, the mode is stated in four places: the header pill, the stage caption
("monitoring, not measurement"), the status payload, and the scan-cycle row
label. **A viewer must never have to guess which one they are reading.**

## HTTP endpoints

| Endpoint | Returns |
|---|---|
| `/` | The page |
| `/stream.mjpg` | Composite as `multipart/x-mixed-replace` MJPEG |
| `/cam/<i>/snapshot.jpg` | One camera's overlaid frame |
| `/status.json` | Everything in the panels |
| `/events.json?since=<id>` | Events newer than `<id>` |

`tools/demo_server.py` serves the **same endpoints** with synthetic data, which
is how the page was built with no hardware attached. The only difference it can
observe is `status.source`.

The scan loop runs in one background thread and publishes finished JPEGs;
handlers only read what was published. No number of viewers can slow a scan, and
a scan is never half-published.

> **No authentication, binds `0.0.0.0`.** Anyone who can reach the Jetson can
> watch. Fine on a lab network, not fine on an open one.
