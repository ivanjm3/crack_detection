# CrackNet on Jetson Orin Nano — work log, 16 Sep 2026

Goal: get the trained CrackNet model running live on the Jetson with the C920,
following `setup.md.txt`. Ended up also fixing false positives and camera
exposure.

Board: Jetson Orin Nano 8 GB, L4T R36.5.2 (JetPack 6.2.3), user `sarah`,
reached from this PC at `192.168.55.1` over the USB link.

---

## 1. Network

**Problem.** Ethernet cable was plugged in but the Jetson had no internet.

**What we found.** Link was fine — carrier up, 1000 Mbps negotiated. But
`dhclient` sent DHCPDISCOVER five times and got zero replies; NetworkManager
timed out at 45 s and retried in a loop. Nothing on that LAN answers this MAC
(`3c:6d:66:bf:3a:b2`). On a campus network that normally means the port needs
the MAC registered.

**Fix.** Gave up on ethernet, connected Wi-Fi instead:

```bash
nmcli device wifi connect 'IOT-PROJ' password '<pw>' ifname wlP1p1s0
```

Got `172.16.61.175/24` via gw `172.16.61.1`.

**Two gotchas on that network.**

- ICMP is filtered. `ping 8.8.8.8` fails even when internet works fine. Test
  with HTTP instead (`curl -o /dev/null -w '%{http_code}' http://ports.ubuntu.com`).
- NTP (UDP 123) is blocked, so `timedatectl set-ntp true` never syncs.

**Clock.** The RTC was 5 days slow (thought it was 11 Sep). This broke apt
outright:

```
E: Release file for .../jammy-updates/InRelease is not valid yet
   (invalid for another 4d 14h 45min 13s)
```

Fixed by setting the clock from an HTTP `Date` header, then `hwclock --systohc`.
After that `apt update` was clean.

## 2. JetPack was not installed

**Problem.** Bigger than expected — the board had a bare L4T rootfs. No
`tensorrt`, no `/usr/src/tensorrt/bin/trtexec`, no `cv2`, no `pycuda`, no
`pip3`, no `v4l-utils`. Everything in `setup.md` from §3 onward was blocked.

**Fix.** `sudo apt install -y nvidia-jetpack` (6.2.3+b81, 80 packages, several
GB). Then the rest of §2.5:

```bash
apt install -y python3-pip python3-dev v4l-utils libv4l-dev \
               gstreamer1.0-tools gstreamer1.0-plugins-good
pip3 install -c constraints.txt "numpy<2" pycuda onnx onnxruntime
```

**Result.** TensorRT 10.3.0, CUDA 12.6, cv2 4.8.0, numpy 1.26.4, pycuda 2026.1,
onnx 1.22.0, onnxruntime 1.23.2.

## 3. Power mode — `setup.md` is wrong here

**Problem.** §2.2 says `nvpmodel -m 0` for max performance. Ran it and the
board dropped from 25 W to 15 W.

**Cause.** This board's `/etc/nvpmodel.conf`:

```
< POWER_MODEL ID=0 NAME=15W >
< POWER_MODEL ID=1 NAME=25W >     <- default
< POWER_MODEL ID=2 NAME=MAXN_SUPER >
```

Mode 0 is the *lowest* setting, not the highest.

**Fix.** `nvpmodel -m 2` + `jetson_clocks`. CPU 1.73 GHz, GPU 1020 MHz.

Also skipped §2.4 (swap) — the board already has 3.7 GB zram and 422 GB free.

## 4. Engine build and parity

Model came over already on the Jetson at
`~/Desktop/crack_outputs/crack_outputs/`; staged into `~/cracknet` and verified
SHA256 against the copy on this PC.

ONNX contract checked on-device: `input [1,3,512,512]` → `logits [1,1,512,512]`,
opset 18, self-contained. TensorRT 10.3 parses opset 18 fine, so **§3.3's
opset-17 re-export was not needed**.

| | |
| --- | --- |
| FP16 engine | **8.77 ms** GPU compute, 113.7 qps |
| FP32 engine | 18.44 ms |
| Ratio | 2.1× — matches §8's "about 2×" |

FP16 beat `setup.md`'s 15–30 ms estimate by a wide margin.

**Parity problem.** §5 needs CRACK500 val images. There are none — on the
Jetson or this PC. `crack500_val.json` only contains Colab Drive paths
(`/content/drive/MyDrive/...`).

**Fix.** Wrote `capture_samples.py` to grab C920 frames as parity inputs, and
rewrote `check_parity.py` to take `--dir` and to report what fraction of pixels
clear the threshold — so a vacuous pass (model outputs ~0 everywhere, trivially
0 disagreement) is visible instead of hidden.

**Result.** 0.0552 % mask disagreement, bar is 0.1 % → PASS. Not vacuous: 38 %
of pixels cleared the threshold.

## 5. Camera — the exposure lock doesn't stick

C920 detected as `046d:08e5` (guide says `082d`; just a different hardware
revision). MJPG available at 1280×720 and 1920×1080.

**Problem.** §4.2's controls apply cleanly, and `v4l2-ctl` confirms them. But
open the stream with OpenCV and `exposure_time_absolute` jumps 156 → 312. So
live inference was running at double the intended exposure — exactly the motion
blur §4.2 exists to prevent. `focus_absolute` was unaffected.

Setting `exposure_dynamic_framerate=0` did **not** help.

**Cause.** C920 firmware drops out of manual mode during stream init and
ignores exposure set before streaming starts. Confirmed later against a
linux-media report of the same bug.

**Fix.** `open_c920()` now reads 5 frames to get the stream running, *then*
shells out to `camera_setup.sh`. Verified holding at 156 through a full run.

## 6. Network viewer

Built `serve.py` — stdlib MJPEG server, no Flask. Capture+inference runs on one
background thread and publishes the latest JPEG, so viewers can't slow
inference down. Endpoints: `/`, `/stream.mjpg`, `/snapshot.jpg`, `/status.json`.

Two bugs while building it, both mine:

- `class Server(ThreadingMixIn, ThreadingHTTPServer)` → `TypeError: Cannot
  create a consistent MRO`. `ThreadingHTTPServer` already includes the mixin.
- `pycuda.autoinit` creates the CUDA context on the **main** thread, and a CUDA
  context belongs to one thread at a time. The pipeline thread died with
  `invalid device context - no currently active context?`. Fixed by pushing the
  context onto the worker thread.

Also silenced a traceback that fired on every closed browser tab
(`ConnectionResetError` in `handle_one_request`).

Verified from this PC over the network: HTTP 200, ~55 KB JPEG, 15–19 fps.

## 7. False positives on people, curtains, desks

**Problem.** Pointed at a person, the model reported `CRACK cov=19%`.

**Cause — this is not a tuning bug.** The model is a single-channel U-Net with
a sigmoid and no abstain path. It was trained on CRACK500, where *every image
contains a crack*, so its prior is "there is a crack here, find it". Given an
image with no pavement it still partitions the frame into more- and
less-crack-like regions. It has no way to say "this isn't pavement".

For scale: CRACK500 masks average **6.3 %** crack pixels. The false positive
was three times denser than a real crack.

**Fix (partial).** `clean_mask()` only filtered on area, which can't tell one
huge crack from one huge blob. Added two geometric tests:

- **mean half-width** = area / perimeter — a stroke of width *w* gives ≈ *w*/2,
  so it reads thickness directly
- **solidity** = area / convex-hull area — filaments fill little of their hull,
  blobs fill most of it. Only applied to large components.

Area comes from the connected-component pixel count, **never**
`cv2.contourArea`, which collapses to ~0 for a 1-px line and would reject real
cracks.

**Measured** (`analyze_blobs.py`, 51 components):

| | synthetic thin crack | false blobs |
| --- | --- | --- |
| half-width | 1.94 px | median 11.2 px, max 43 |
| solidity | 0.041 | median 0.715, max 1.09 |
| outcome | kept | 96.2 % of coverage removed (38 % → 1.44 %) |

**Near-miss worth recording.** Almost set `max_halfwidth` to 8 px, since the
false blobs cluster at 11. But CRACK500's 6.3 % average implies real cracks up
to ~25 px wide (half-width ~12), so that would have silently started dropping
wide cracks. Left at 12, favouring recall. No in-domain crack images on the
device to validate against.

Also raised `--alert-frac` 0.002 → 0.01. The old value fires at the ~0.06 %
speck level a clean surface produces.

**Result.** Same scene: `CRACK cov=19%` → `clear cov=0.45%`.

**Still not solved.** This is a post-hoc filter. The model still confidently
produces those blobs; we just discard them. Anything with elongated dark
features (wood grain, grout, cables, wrinkled fabric) will pass a thinness test.
A real fix needs a surface-gate classifier or fine-tuning with hard negatives.

## 8. Auto-exposure — three designs, two failed

**Problem.** Fixed exposure is scene-specific. On a white wall the sensor
saturates, large areas pin at 255, and a hairline crack's contrast is destroyed
*at the sensor* — no downstream contrast processing can recover it.

Also found: **`gain` was pinned at 255, its maximum** (default 0), left there by
the firmware's own auto-exposure before manual mode was set. High gain turns
sensor noise into thin bright streaks — exactly what the model hunts for.

### Attempt 1 — target 99th-percentile luma at 235

**Failed.** Limit-cycled. Exposure swung 311 ↔ 532, hitting 4.8 % clipping every
few seconds. On a bimodal scene (dark room + bright window) p99 never reaches
235 — it's either ~216 or saturated — so the loop wound up until the highlights
blew out, cut hard, and repeated.

### Attempt 2 — add a monotone anti-windup ceiling

**Failed, worse.** Fine on a static scene; catastrophic on a camera that gets
re-aimed. Pointed at a white wall, clipping ratcheted the ceiling down until it
fell *below* `EXP_MIN=3`. That made this branch fire at the exposure **floor**
instead of the ceiling:

```python
self.ceiling = min(self.ceiling, self.exp * 0.9)   # only ever decreases
if self.exp >= self.ceiling - 1:                   # exp=3, ceiling=2.7 -> True
    self._apply_gain(self.gain + 16)               # cranks gain at the FLOOR
```

End state, confirmed live: `exposure=3, gain=255`. Darkest shutter, noisiest
gain, and since the ceiling relaxed 5 % per 4 updates from 2.7, no way back.
Both reported symptoms — "goes dark on a white wall" and "stays dark
afterwards" — came from this one bug.

**Lesson: no one-way ratchet in a controller for a camera that gets re-aimed.**

### Attempt 3 — damped proportional onto a reachable target (works)

- Control metric is **median** luma → 120 (mid-grey). Always reachable, so no
  ratchet is needed to stay stable.
- Strict two-stage ladder: brighten = exposure first, gain only at *max*
  exposure; darken = gain first, then exposure. Makes `exp=3, gain=255`
  unreachable by construction.
- Trade gain down for exposure once converged. Without this it settled at
  `exp=71 gain=111` — correct brightness, needless noise.
- Exposure capped at 500 (50 ms). The device max of 2047 is a 205 ms shutter:
  heavy motion blur and a ~5 fps cap.

### The thing that took longest to spot

Frame transients. At a **fixed** `exposure=500 gain=0`, consecutive medians
measured **4** and **241**. The C920 emits black/blown frames for several frames
after any control change, and the loop was treating them as real measurements.
`CAP_PROP_BUFFERSIZE=1` does not prevent it. Fixed by flushing in-flight frames
with `cap.grab()` after every change, staying blind ~0.5 s, and smoothing the
metric with an EMA.

### Testing — the live room was useless for this

With someone moving in frame the median swings 19 ↔ 178 **at fixed settings**,
so live pass/fail is noise. Spent several rounds chasing that before giving up
on it.

Wrote `test_ae_sim.py` instead: drives the real controller against a modelled
sensor including actuation lag and garbage frames. Deterministic.

```
mid-grey, from default           exp=247 gain=  0  luma=126.0  PASS
STUCK DARK (exp=3,gain=255)      exp=232 gain=  0  luma=118.3  PASS
stuck bright (exp at cap)        exp=239 gain=  0  luma=121.9  PASS
white wall (high reflect)        exp=128 gain=  0  luma=124.0  PASS
white wall, from stuck dark      exp=125 gain=  0  luma=121.1  PASS
dark asphalt (low reflect)       exp=500 gain= 44  luma=117.3  PASS
very dark scene                  exp=500 gain=160  luma= 88.4  PASS (at caps)
7/7
```

Then confirmed on the real camera: median recovered 35 → 108 → 128, exposure
rode to the cap and settled back to ~270, gain stayed 0.

## What worked / what didn't

**Worked**

- Wi-Fi instead of ethernet
- Clock from HTTP `Date` header (NTP blocked)
- `nvpmodel -m 2`
- FP16 engine — 8.77 ms, well under estimate
- Webcam frames as parity inputs
- Re-applying camera controls *after* stream start
- Shape filtering — 96 % of false-positive coverage removed
- Median-target AE with a two-stage ladder
- Simulated sensor for testing the control law

**Didn't work**

- Ethernet DHCP — no lease, needs MAC registration
- `nvpmodel -m 0` — lowers power on this board
- `exposure_dynamic_framerate=0` — doesn't stop the exposure reset
- `CAP_PROP_BUFFERSIZE=1` — doesn't stop post-change garbage frames
- p99-target AE — limit cycle
- Anti-windup ceiling — drove exposure to floor + gain to max, unrecoverable
- Tuning/validating AE against the live room — too noisy to measure

**Not attempted**

- §9 systemd boot service (persistent change, left for approval)
- §7 threshold tuning on real pavement — needs the camera aimed at pavement
- Surface-gate classifier / fine-tuning with hard negatives
